# StatCalc — Спецификация проекта

**Веб-платформа статистических расчётов для биологии и агрономии**

Версия документа: 1.0
Дата: 21 июля 2026
Статус: архитектура согласована, переход к реализации

---

## 1. Суть проекта

Веб-сайт, на котором пользователь загружает свои данные и выполняет статистические
расчёты. Тяжёлые вычисления идут не на сервере проекта, а на стороне пользователя
(браузер / его собственные облачные ресурсы). Это ключевое архитектурное решение,
которое почти обнуляет серверные расходы.

**Предметная область зафиксирована: статистика в биологии.** Референс — учебник
Welham, Gezan, Clark, Mead «Statistical Methods in Biology: Design and Analysis of
Experiments and Regression» (CRC Press, 2015). Область сужена намеренно: универсальный
калькулятор «для всех сфер» размывается и ничего не делает хорошо. Привязка к книге
даёт готовый scope, эталон для сверки чисел и определённую аудиторию (биологи,
агрономы, экологи).

**Аудитория:** технически подготовленные пользователи — те, кто понимает
программирование и статистику хотя бы на начально-среднем уровне. Это меняет дизайн:
не упрощаем, а даём прозрачность и контроль.

## 2. Ключевые архитектурные решения

### 2.1 Тройная модель вычислений (tiered compute)

Расчёт выполняется на одном из трёх уровней в зависимости от объёма данных и типа
операции:

| Уровень | Где считает | Для чего |
|---|---|---|
| **1. Браузер (CPU)** | WebAssembly / Pyodide у пользователя | Малые датасеты, базовая статистика. Мгновенно, ноль серверных расходов, максимум приватности. Большинство пользователей остаются здесь. |
| **2. Локальный GPU** | WebGPU (видеокарта пользователя) | Параллелизуемые задачи: bootstrap, Монте-Карло, большие матрицы. Всё ещё на клиенте. |
| **3. Cloud** | Облачный GPU по ключу пользователя | Тяжёлое: данные не влезают в память клиента, большие модели. |

### 2.2 Ручной выбор бэкенда, не автоматический

Поскольку аудитория подготовленная, бэкенд выбирает пользователь сам — автороутинг
раздражал бы тех, кто знает, что делает. Система показывает доступность (есть ли
WebGPU, сколько памяти), но решение за пользователем. Выбор — **per-operation**
(на каждый расчёт), а не глобальный на сессию.

### 2.3 «Bring your own compute» для облака

Проект НЕ держит собственный GPU-сервер. Для облачных расчётов пользователь подключает
свой API-ключ (Modal / RunPod и т.п.) и платит за вычисления сам. Это снимает с проекта
и денежную нагрузку, и часть ответственности за данные.

### 2.4 Два типа облачных вариантов

«Cloud» распадается на два принципиально разных механизма — их нужно визуально
разделять в интерфейсе:

**Тип A — исполняемые бэкенды (реальная авто-интеграция):**
Modal, RunPod, Lambda Labs, vast.ai. Есть REST/SDK API. Пользователь даёт ключ → сайт
программно отправляет задачу → получает результат. Пользователь жмёт «Запустить» и ждёт.

**Тип B — генераторы артефактов (пользователь исполняет сам):**
Colab, Kaggle, Docker. У них НЕТ публичного API «прими задачу — верни результат».
Здесь сайт генерирует готовый артефакт (`.ipynb` ноутбук с данными и кодом, или
`Dockerfile` + скрипт), пользователь скачивает и запускает у себя. Данные не проходят
через сервер проекта.

| Вариант | Механизм | Данные через сервер проекта? |
|---|---|---|
| Браузер | Исполняется у пользователя | Нет |
| Локальный GPU | WebGPU у пользователя | Нет |
| Modal / RunPod | API-ключ, авто-исполнение | Транзитом (проверить: возможно напрямую браузер→API) |
| Colab / Kaggle | Генерация `.ipynb`, юзер запускает | Нет |
| Docker | Генерация образа, юзер запускает | Нет |

## 3. Валидация качества данных

### 3.1 Почему это критично

Отвечаем за результат. Данные из Excel при конвертации в CSV дают классические дефекты:
разные форматы дат в одной колонке, числа, интерпретированные как строки или даты,
смешанные типы. Проверять нужно тщательно, на уровне каждой ячейки.

**Важно:** тщательная per-cell валидация на гигабайтах — это реальная вычислительная
нагрузка (миллиарды операций парсинга/regex), НЕ бесплатный шаг. Но ускоряется она
**не GPU** (строковый парсинг с ветвлениями плохо ложится на GPU), а векторизацией,
многопоточностью и стримингом.

### 3.2 Двухтировая проверка

**Тир 1 — сэмпл-скан (секунды, всегда):**
Читается не весь файл, а срез (первые ~10k строк + случайные чанки из середины/конца
через seek по файлу — начало нерепрезентативно). Определяет кодировку, разделитель,
десятичный знак, заголовок, типы, грубую долю пропусков, смешанные типы. Выдаёт
вероятностную оценку и экстраполяцию («ожидается ~24k проблемных ячеек»). Ограничение,
которое честно показываем: сэмпл может пропустить редкий дефект — это скрининг, не
гарантия.

**Тир 2 — полная проверка (минуты, по запросу):**
Проходит каждую ячейку. Запускается когда сэмпл нашёл проблемы, или результат критичен,
или пользователь явно затребовал. Выдаёт точную карту: сколько проблем, в каких
колонках, в каких строках (номера — чтобы пользователь исправил у себя).

### 3.3 Skip проверки

Пользователь может пропустить проверку. Обоснование двойное: (а) вычислительное — на
2 ГБ полная проверка занимает минуты, тот кто уверен в данных не должен ждать;
(б) UX — эксперт, почистивший данные сам, не хочет нотаций. Но всегда идёт быстрый
Тир 1, если только пользователь не отключил явно.

### 3.4 Предупреждение вшивается в результат

Если данные имели дефекты и пользователь всё равно посчитал — пометка едет вместе с
результатом и в экспорт: «Результат получен на данных с предупреждениями: 12% пропусков
в колонке X, тест Шапиро-Уилка отклонил нормальность (p<0.001)». Через месяц пользователь
видит контекст качества прямо у цифр. Это «отвечаем за результат» на практике.

### 3.5 Инструменты парсинга/валидации

- **polars** — основной движок. Многопоточный, ленивый (lazy), стриминг больше-чем-RAM.
  Закрывает многопоточность, чанки и память одним инструментом.
- **pyarrow** — многопоточное чтение, строгая типизация, движок чтения под капотом.
- **DuckDB** — SQL по CSV/Parquet без полной загрузки в память; для аналитических
  проверок колонок.
- **PapaParse** (JS) — лёгкий стриминговый парсинг в браузере для первичной загрузки
  и предпросмотра.
- **pandas** — только для того, что уже влезло в RAM и провалидировано, не для
  валидации гигабайтов.

**Ограничение уровня:** Pyodide в браузере ограничен памятью вкладки (~2–4 ГБ потолок).
Гигабайтная полная проверка физически принадлежит локальному/cloud бэкенду, не браузеру.
Браузер тянет максимум Тир 1 на сэмпле.

## 4. Формат отчёта валидации

Четыре слоя от сводки к деталям, все рендерятся из ОДНОЙ внутренней модели отчёта.

**Слой 1 — сводка (сразу на экране):** вердикт одной строкой + цвет + иконка + текст
(дальтоники, ч/б экспорт). Ключевые цифры (строк, колонок, % проблемных ячеек). Топ 3–5
проблем по серьёзности. Пометка охвата (сэмпл N/M или полная).

**Слой 2 — детали по колонкам (по клику):** отчёт колонко-центричный (пользователь
мыслит колонками). По каждой: тип + уверенность, конфликты типов с примерами реальных
битых значений, пропуски (число, %, что считалось пропуском), для дат — обнаруженные
форматы и неоднозначные примеры (03/04/2020 — тихий killer), выбросы (как info, не
error), дубликаты. Проблемные колонки вверху развёрнуты, чистые внизу свёрнуты.

**Слой 3 — карта ячеек (только полный тир):** координаты строка+колонка+значение+причина.
Не вываливать всё в DOM — первые ~100 + «скачать полный список». Фильтр/сортировка.

**Слой 4 — экспорт:** JSON (машиночитаемый, полный — главный для тех. аудитории),
CSV проблемных ячеек (плоский список для правки в Excel), читаемый отчёт (Markdown/HTML/PDF).

**Привязка к результату:** сводка качества вшивается в экспорт любого расчёта (охват,
предупреждения, seed сэмпла). Skip тоже фиксируется («проверка пропущена пользователем»).

## 5. Стек

### 5.1 Расчётное ядро — Python

`numpy`, `scipy`, `pandas`, `statsmodels`. Чистые статистические функции, тестируются
отдельно от UI. Тот же код исполняется в браузере через Pyodide — не переписываем на JS.

### 5.2 Браузерный рантайм — Pyodide

Python-код едет в браузер как WASM. Тяжёлый на первичную загрузку (десятки МБ),
но кешируется.

### 5.3 Фронтенд — React + Vite + TypeScript

Выбор обоснован: индустриальный стандарт, экосистема закроет любую потребность (таблицы,
графики, загрузка), навык остаётся. Streamlit отклонён — упрёшься в потолок ровно там,
где нужен кастомный UX для продвинутых. TypeScript обязателен — типизация данных/колонок/
результатов спасает часы отладки.

### 5.4 Остальное

- **Сборка/деплой:** Vite + Vercel (или Cloudflare Pages).
- **Графики:** Plotly.js или Observable Plot (боксплоты, гистограммы, scatter, Q-Q).
- **Таблицы:** TanStack Table (виртуализация — не рендерит 100k строк в DOM).
- **Тесты ядра:** pytest против SciPy/statsmodels-эталона.
- **НЕ берём на старте:** бэкенд-сервер, БД, GPU-либы, cloud-SDK — это фаза 6+.

### 5.5 Human-friendly для технической аудитории

Означает противоположность упрощению: прозрачность (виден метод, формула, backend,
время), клавиатура и скорость (хоткеи, вставка из буфера, drag-drop), разумные дефолты
+ полный контроль, история сессий, возможно API самого сайта.

### 5.6 Языки

UI-локализация RU + EN минимум, строки в словарях с первого дня (ретрофит i18n мучителен).
Отдельно — locale чисел (десятичный разделитель, это про парсинг данных, не про UI-язык)
и статистическая терминология (n vs n−1 в стандартном отклонении — показывать определения).

## 6. Охват статистических методов (по книге)

Полное покрытие книги — **цель (дорожная карта)**. Реализация — **поэтапная, по главам,
от простого к сложному**. Причина: главы 14–16 (GLM, REML, смешанные модели) — тяжёлая
артиллерия, одна корректная реализация REML — отдельный большой проект. Пытаться сделать
всё сразу = не выпустить ничего.

### Блоки книги

**Основы (гл. 1–4):** введение, обзор классической статистики (описательная,
распределения, доверительные интервалы, проверка гипотез), принципы дизайна эксперимента.

**Регрессия (гл. 5–7):** простая линейная регрессия, проверка допущений (диагностика
остатков), множественная регрессия.

**ANOVA / дисперсионный анализ (гл. 8–13):** ядро книги. Однофакторный ANOVA, множественные
сравнения, блочные схемы (randomized blocks), факторные схемы, сложные планы (split-plot).

**Продвинутое (гл. 14–16):** обобщённые линейные модели (GLM), смешанные модели (REML),
нелинейная регрессия.

### Модуль диагностики — приоритетный

`diagnostics.py` (проверка допущений: нормальность, гомоскедастичность, независимость
остатков, Q-Q plot) проходит через всю книгу и всю прикладную статистику. Именно это
отличает серьёзный инструмент от калькулятора p-value. Четыре графика с обложки книги
(scatter, residual plot, гистограмма, Q-Q) — визуальное ядро диагностики.

### Предупреждение по эталону ANOVA

Книга исторически связана с GenStat/R, не с Python. Типы sum of squares (Type I/II/III)
и схемы множественных сравнений имеют РАЗНЫЕ конвенции в разных пакетах — числа могут
расходиться не из-за ошибки, а из-за методики. Когда дойдём до ANOVA: явно зафиксировать,
какой конвенции следуем (книжной / R / statsmodels). Для t-тестов и регрессии проблемы
почти нет, для ANOVA — есть.

## 7. План реализации (вертикальными срезами)

Принцип: каждая фаза даёт работающий, потрогаемый результат. Один тонкий, но ПОЛНЫЙ путь
(загрузил CSV → посчитал → получил результат), затем расширение. НЕ строим горизонтальными
слоями («сначала вся валидация, потом все бэкенды») — так полгода нет ничего рабочего.

**Фаза 0 — Фундамент:** зафиксировать MVP-scope (список методов v1), формат данных v1
(только CSV, только браузер), репозиторий, структура.

**Фаза 1 — Расчётное ядро:** чистая статистика отдельно от UI. Реализовать методы v1,
покрыть pytest против SciPy/statsmodels-эталона. Заложить seed и структуру результата.
→ Доверенное ядро.

**Фаза 2 — Ядро в браузере:** поднять Pyodide, прогнать ядро в WASM, убедиться что числа
те же, замерить лимиты браузера. → Статистика считается в браузере, ноль серверных расходов.

**Фаза 3 — Загрузка и парсинг:** самая коварная часть, заложить непропорционально много
времени. Загрузка (drag-drop), детекция (кодировка/разделитель/десятичный/типы),
предпросмотр с ручным override, Тир-1 валидация. → Пользователь доходит от кривого CSV
до расчёта.

**Фаза 4 — Минимальный UI и запуск:** собрать 2–3 в интерфейс (загрузил → предпросмотр →
метод → результат → экспорт). → **Работающий MVP.** Домен + Vercel free. Показать людям.

**Фаза 5 — Обратная связь и стабилизация:** дать MVP реальным пользователям, чинить где
спотыкаются (почти наверняка — парсинг), добить методы v1, привести UX в порядок.

**Фаза 6+ — Расширение по спросу (не раньше):** локальный GPU (WebGPU), полная валидация
+ polars/streaming, cloud-бэкенды, генераторы артефактов (Colab/Kaggle/Docker), аккаунты/
история/API. Следующие главы книги (множественная регрессия → факторный ANOVA → блочные
схемы → GLM → смешанные модели), каждая — новый релиз.

### MVP-срез v1 (главы 1–5)

- Описательная статистика, доверительные интервалы (гл. 2)
- Проверка гипотез: t-тесты + непараметрические аналоги (гл. 2)
- Однофакторный ANOVA + множественные сравнения (гл. 3, 8)
- Простая линейная регрессия + диагностика остатков (гл. 5)

Покрывает ~80% реальных задач биолога/агронома, всё валидируется против SciPy/statsmodels.

- `core/` физически отделён от `web/` — самостоятельный Python-пакет, тестируется сам
  по себе, переиспользуется браузером через Pyodide. Готов и к CLI/серверному API в будущем.
- `report/schema.py` — единая модель: и результат, и отчёт валидации в одной схеме, из неё
  все экспорты. Сэмпл и полный тир пишут в одну схему.
- `pyodide/bridge.ts` — единственная точка контакта JS↔Python. Добавишь другой бэкенд —
  меняешь только мост, не весь UI.
- `components/` по фичам (каждая папка самодостаточна), не размазано по styles/logic/views.

**Порядок работы:** начинаешь с комфортной зоны (Python-ядро в VS Code + pytest), React
осваиваешь когда ядро уже работает и мотивация подкреплена видимым результатом.

## 9. Финансовые расходы

Главная статья — не деньги, а время. Архитектура (вычисления у пользователя / по его
ключу) обнуляет самую дорогую статью таких проектов — серверный GPU-compute.

| Сценарий | Стоимость |
|---|---|
| MVP на free-тирах (домен + Vercel free + serverless free, без аккаунтов) | ~$15/год (только домен) |
| Рабочий запуск (домен + платный хостинг + БД + email + мониторинг) | ~$50–80/мес |
| С ростом трафика | ~$100–200/мес |

Бесплатно: весь Python-стек (open source), GitHub, SSL (Let's Encrypt), GPU/cloud
(платит пользователь своим ключом). Платить больше начинаешь когда появляется трафик —
то есть когда проект уже что-то доказал.

**Безопасность с первого дня — чужие API-ключи (Modal/RunPod):** никогда не хранить на
сервере в открытом виде, лучше вообще не хранить — держать в браузере (сессия/локально
с шифрованием), пробрасывать только на время запроса. Утечка = чужие деньги = юридический
кошмар. Это не денежный расход, но нельзя откладывать на потом.

## Приложение: сквозные принципы

1. **Вертикальный срез, а не горизонтальные слои** — полный тонкий путь, затем расширение.
2. **Не строить всё из этого документа сразу.** Всё спроектировано и записано, но
   реализуется по мере надобности. MVP на браузерном уровне покрывает большинство сценариев.
3. **Отвечаем за результат** — качество данных задокументировано в самом артефакте расчёта.
4. **Прозрачность вместо сокрытия** — аудитория подготовленная, показываем метод/формулу/
   backend, не прячем «сложное».
5. **Единые модели** — один отчёт-объект, один JS↔Python мост, одна i18n-система: не
   дублировать логику под разные выводы.
